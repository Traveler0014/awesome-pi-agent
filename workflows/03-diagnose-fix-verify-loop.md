# 03 · 诊断 → 修复 → 验证闭环

## 背景

最大的时间黑洞是「改了又错、错了再改」的回归循环。能明显看到：**先验证、再提交**的工作方式几乎不回炉。

## 闭环三步

```
1. 诊断    → 编辑后立刻 lsp_diagnostics / /lsp-status，拿到类型错误
2. 修复    → 最小改动（edit），不顺手重构无关代码
3. 验证    → 重跑 lsp_diagnostics + 相关测试 + 手动走一遍受影响路径
```

pi-lsp 的意义：不用跑完整构建（tsc/build 很慢），改完一个文件就拿到诊断。

## 关键规则

- **先 lsp_diagnostics 再继续**：编辑后立刻验证，不要攒一堆再查。
- **最小改动**：scope 越大越容易引入回归。
- **重构后必回归**：重构引入过「功能隐身、路由失效、面板错位」这类回归，全是在重构后没验证旧功能。
- 本地临时忽略用 `.git/info/exclude`，别为局部调试改 `.gitignore`。

## 可复制提示词

```text
在这个仓库里跑一个自愈循环：
1. 我说一个失败的测试或 bug；
2. 你自动诊断根因（lsp_diagnostics + 读代码）、做最小修改、跑相关测试；
3. 迭代直到全绿；
4. 最后总结根因、改动与验证结果。
```

## 教训

- 大量 buggy 改动来自**没有边界验证**：空输入、超时、时区、编码。写测试时优先覆盖边界。
- 长调试循环时，把「复现 → 隔离 → 修复 → 验证」写下来再动手，比直接改更省时间。
