# 05 · 上下文可见性与受控压缩

## 背景

长会话真正的失败模式不是「装不下」，而是**「以为装不下」**：

- 模型对剩余空间的估计长期偏高（实测常常是 6~29% 占用时就开始慌了）；
- compaction 摘要里留下的旧自估会锚定后面上百轮；
- 默认 `reserveTokens=16384` 把 1M 窗口的自动压缩推到 ~98%——**必然发生在任务中间**。

`pi-context-manager` 给的是可见性（纠偏）+ 受控操作（带护栏），而不是「更用力地自动压缩」。

## 三条通道

| 通道 | 何时用 | 代价 |
|---|---|---|
| 系统提示里的 `[context-manager] window … soft-limit …` | 每轮自动在，作为常量参考 | 窗口级常量，缓存友好 |
| 里程碑消息（追加式） | 跨过阈值时提示一次 | 只追加，不改写前缀 |
| `context_status`（只读工具） | 开工前 / 长任务规划前 | 一次工具往返 |

`/context-manager` 命令看同一份数据。

## 规则

1. **只在任务边界 compact**：一次批处理结束、报告交付之后。中途调用会被护栏拒绝——而且每压一次都让 prompt cache 失效，很贵。
2. **keep 清单写事实，不写感想**：决策、被否决的路径、确切命令、任务 ID / PR 号。总量 ≤ 窗口 5%。
3. **prune 前先落盘**：`externalizedTo` 是必填参数，先把原始输出写文件；只丢「已经落盘、短期不会再逐字读」的旧工具结果。
4. **被拒绝时信真实用量**：低收益 / 冷却 / 已有排队任务时工具会拒，并回传真实 usage——按它纠偏，别继续凭猜。
5. **不要连续压**：同一 run 里压两次、或者压缩完马上又压，都是纯浪费。

## 可复制提示词

```text
先 context_status，报告真实占用和距 soft-limit 的距离。
如果已过 70%，我们先在当前任务边界收尾，再决定是否 compact。
压缩时把下面这些逐字保留：<决策 / 被否决的方案 / 确切命令 / 任务 ID>。
```

```text
这批工具输出已经写到 <file>。把前 N 条最大的旧结果 prune 掉，
之后再继续，别让我重新读它们。
```

## 教训

- 先量再决定：`context_status` 一次调用，比凭感觉提前压缩便宜得多。
- 摘要里的「上下文快满了」会变成自我实现的预言——不要继承上一轮的估计。
- 上下文管理是**策略问题**（什么时候压、留什么），不是工具问题；护栏存在的意义就是防止模型自己乱按按钮。
